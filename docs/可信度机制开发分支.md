## 接收范围

- 地面观测估计、局部缺测补足、连续可信度及其证据来源。
- 可通行快照中的可信度和有效地面高程、增量更新与缓存失效。
- 可信度路径代价、路径简化，以及起终点、支撑和路径边对有效高程的消费。
- 相关设计、回归测试、离线对照、性能验证与平台适配。

可信度表示工程证据分数，不作为经过校准的通行概率。P3 原始输入保持可追溯，补值不递归成为
原始观测；明确障碍、未知区域和平台物理约束需要独立验证。定位、传感器误差模型、探索收益或
其他新增机制若纳入本专题，先明确设计范围与验收证据。

## 开发、验证与同步流程

1. 从 `dev/terrain-confidence` 创建独立专题子分支与工作树，或在专用开发工作树中进行单项开发。
2. 明确改动范围、输入证据、行为变化及回归场景；实现和设计一起进入开发分支。
3. 在开发分支的确定提交上构建并测试。验证记录包含提交、配置、环境、命令、退出状态、结果和
   仓库外产物路径。不能混用来源应用工作树的构建结果。
4. 通过下述适用门槛后，将通用结果合入 `integration/pure-planner-orin`，在合并结果上重新验证。
5. 向应用分支同步已验证结果，并分别验证足式、轮式和 TCP 的适配与配置。应用差异通过明确的
   适配提交保留；存在无关祖先提交时先确定同步范围，不能强行进行整分支合并。

现有机制已进入开发分支。后续正式合并应有明确的合格提交与验证记录，未合格修改继续留在开发分支。

## 合并门槛

- 核心与 ROS 的受影响包构建、测试通过；缓存、增量更新和有效高程读写一致。
- 回归覆盖密集/稀疏观测、单侧/共线支持、台阶/坑/薄障碍、全空白、零权重、平台差异和
  实际路径的可信度偏好。保留隐藏窄坑反例，不以补足率或高可信度代替安全证明。
- 固定同输入、同配置的前后对照，明确可通行状态、规划结果与性能变化；记录全量与增量开销。
- 设计与验证记录更新，明确已实现范围、证据、已知限制和未执行项。
- 本机 Jazzy 算法测试与生产 Humble 构建验证分开。应用部署前另验 Orin 性能、DDS/输入回放和
  对应控制闭环；未执行项标为 `NOT_RUN`，不能以本机通过代替设备验收。
