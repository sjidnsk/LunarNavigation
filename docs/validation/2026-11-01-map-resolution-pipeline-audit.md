# 5cm地图全链路影响与瓶颈审计

任务：GLOBAL-PLANNING-PERF-20261101，基线482f8e66；继续原专题，不切正式运行、不改P3/Env_X。测试机192.168.100.216、ARM64、Ubuntu22.04/Humble。

## 范围与方法

此前稀疏几何分辨率对照固定了矩形数量，不能代表高程输入细化后的处理量。本轮直接调用正式安装的NativeTerrain、ExplorationMap、前沿/候选/信息增益库，以及专题的全局worker、真实acados MPCC与认证接口。
相同解析高程场景：平缓斜面、两个0.5m高的圆形凸起、边界UNKNOWN；物理范围16/32/64m见方；源分辨率20/10/5cm。不是将20cm捕获插值后冒充新观测。
地图每组两帧：首次完整输入，随后只将中心格高程增加1mm；计时包含完整消息的实际处理。导航局部窗口固定5m×5m、1cm（500×500）；平台几何/能力与净空不因分辨率放宽。
探索对比分两类：policy/coarse都保留20cm，或一起与源分辨率细化。生产前沿最小长度1m、候选工作量100000/10000/1000000、传感器10m/90度、可见性1000000工作量，均未放宽。
C++测试不启动ROS节点；Python只构造/序列化消息并调用组件，不执行rclpy.init、不发目标或速度。构建与运行串行，避免CPU竞争。首轮配置路径错误产生的失败日志保留，不计入结果；修正为隔离candidate/config/wheel.yaml后重新验证。

5→5cm前沿检测约29–55ms，前沿检测本身不是33s的主要来源；地图Apply与候选碰撞检查更突出。信息增益对首个候选触发visibility work budget exhausted（scored=0）；测试在首个异常处结束本轮评分，不虚构后续候选都已评测。保留工作量上限，不靠直接提高上限宣称解决。
64m即使探索仍20cm，5cm源输入Apply约5194/5824ms，峰值RSS476.2MiB。虽然只有72900个policy格，仍保留1157776个来源片段；保留粗输出不能消除细源格的融合成本。

当前ExplorationMap::Apply遍历有限源格并进行多边形裁切/历史片段合并；有改变后调用DeriveProjected派生图，脏tile仍取全图并集。候选SafePoseValidator按地图分辨率枚举车体覆盖格，可见性按格进行射线工作。这些实现解释了处理量为何会超过单纯的格数增长，但本轮未对Apply内部逐段占比进行CPU剖析，不能把全部33s指定给其中一个函数。

整幅64m×64m任务区域的TaskRaster默认限制实测：20/10cm可构建，5cm返回task raster exceeds configured cell limit。默认1048576格，而5cm整幅需1638400格；只选择更小探索区域时不必触发，不能说所有5cm探索都无法开始。

策略地图导出采用同一真实PolicyMapExporter（16m、首帧一次）：20→20cm约14.5ms、1tile/721249字节；5→20cm约16.0ms、1tile/721249字节；5→5cm约115.4ms、4tiles/2884057字节。tile固定256×256且有填充，因此本例是4倍消息，不把它写成普遍16倍。
DRL读取policy map而不是直接读取P3；只有P3细化不会自动把DRL地图改为5cm。PolicyMapStore按响应resolution_m读取，但策略特征、图构建、可见性与固定Actor效果仍需单独验证。本轮Actor推理/训练NOT_RUN。

## 结论与下一批范围

现在不宜全链路统一5cm。已证明的瓶颈优先级：高程全帧分类/融合、探索细图派生、全局分解图构建、候选碰撞与可见性；局部MPCC求解不是本轮主瓶颈。
后续可先优化既有地图的变更复用、避免单格改动重做全图，优化全局几何分解/连边以及重复几何查询；不增加额外地图实体，不提前实施共享基础地图设计，不放宽碰撞、取消认证或直接扩大工作量上限。保留现有20cm探索输出可控制下游负载，但不能替代源地图处理优化。
P3原生5cm建图、点云覆盖、DDS负载、RViz负载、DRL Actor与车辆闭环NOT_RUN；正式P4未切换，其他项目文件未修改。
